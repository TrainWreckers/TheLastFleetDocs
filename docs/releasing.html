Cutting a playtest release

We want testers to unzip and play, with no setup fuss. So releases are self-contained zips for Windows (x64) and Linux (x64), and the only thing a tester needs to install is a Vulkan 1.3 driver. The Release workflow builds them for us.

Steps

So you're ready for a round of playtesting? Here's the flow:

  1. Make sure main is green in CI and is the build you want tested.

  2. Run the Weekly workflow by hand on main (Actions, Weekly, Run workflow) and wait for it to pass. Pull requests only build on Linux and run the fast GPU smoke test, so this is what checks Windows and the ray-traced, path-traced and device-loss renders before testers get the build.

  3. Tag it and push the tag. Use a playtest version, numbered per round:

    git checkout main && git pull
git tag v0.1.0-playtest.1
git push origin v0.1.0-playtest.1

  4. The Release workflow takes it from there. It runs the tests and publishes both platforms in Release with ReadyToRun. Then it checks that the published build actually runs (headless on both, plus rendering the outpost under software Vulkan on Linux), zips them, and creates a GitHub pre-release named after the tag with TheLastFleet-0.1.0-playtest.1-win-x64.zip and ...-linux-x64.zip.

  5. Send testers the release link.

The version comes from the tag (v0.1.0-playtest.1 is version 0.1.0-playtest.1). It shows up in the window title, the first line of the log, and every playtest report (gameVersion), so you can always tell which build a piece of feedback came from.

Want to try the packaging without making a release? Run the workflow by hand (Actions, Release, Run workflow). The zips come out as workflow artifacts, versioned 0.1.0-dev.<run>.

What is in a zip

  • The game (LastFleet.exe on Windows, LastFleet on Linux) with the .NET runtime.
  • Its native libraries (GLFW, Jolt, meshoptimizer, Dear ImGui, OpenAL Soft). Windows builds also carry NVIDIA Streamline and DLSS (vendor/streamline), because Streamline runs nowhere else.
  • The compiled shaders, and the content folder: the hand-built levels and their encounters, the data in content/defs, the models, animations and sounds, and the BRUTAL logo.
  • The license texts in licenses/. BRUTAL's NOTICE.txt has to ship with every build.
  • PLAYTEST-README.txt for testers, and PLAYTEST-PROTOCOL.md.

By hand

Want the same build on your own machine? Here's how for one platform:

dotnet publish src/LastFleet.Client -c Release -r win-x64 --self-contained -p:Version=0.1.0-playtest.1 -o publish/win-x64

(Use -r linux-x64 for Linux.) Add -p:PublishReadyToRun=true to match the workflow.

Notes

A couple of gotchas:

  • Builds aren't code-signed, so Windows SmartScreen may warn on first run ("More info", then "Run anyway"). Give testers a heads-up so it doesn't scare them off.
  • Settings and reports live in the user's folder, not next to the game, so a new build keeps a tester's settings.
  • Each tag makes a new release. Delete old pre-releases on GitHub when a round is over.
