Modeling and animating characters on a rig in Blender

Soldiers, the Choir's lancers and the players are modeled and animated in Blender on rigs. A rig is a skeleton the game knows about, stored as data in content/rigs/ (the humanoid is the first one: humanoid.json).

Why bother with rigs? Every model on a rig shares the rig's animations (its clips). So a new soldier only needs a model, not a new set of animations, and a new kind of body (a rat, a hound, a spider) is a new rig file, not engine code! This is part of the plan in ../plans/animation.md.

Soldiers and the Choir's lancers are drawn animated from these files. Each enemy variant names its model in content/defs/ai/enemies.json ("model": "lancer" for lancer.gltf). --box-soldiers draws them from boxes, the old way. How the game blends the clips is set by the rig's animation graph, which is a separate file: see animation-graphs.md.

The source files

Start from these in Blender (5.2 or later). They're in content/raw/characters/ and go through Git LFS (if a .blend opens as a few lines of text, run git lfs pull once):

File What it is Exported to
soldier.blend The grey-box soldier: its meshes skinned to the humanoid armature. content/characters/soldier.gltf
lancer.blend The Choir Lancer on the same rig. content/characters/lancer.gltf
player.blend The players' body (yours in first person, with the head hidden by the rig's firstPersonHides). content/characters/player.gltf
humanoid_clips.blend The rig's clips: the armature with every action (Idle, Walk_F, Reload...), plus the soldier on it so you can watch them. content/anim/humanoid.gltf

The naming tells you what a file is:

  • <model>.blend is a model, exported as content/characters/<model>.gltf.
  • <rig>_clips.blend holds a rig's clips, exported as content/anim/<rig>.gltf and shared by every model on that rig.

Each file knows its rig (Rig file, stored relative to the .blend, so it works wherever the repository is). The game reads the .gltf files, and the .blend files are the source for them. So change the .blend and export it. Never edit the .gltf by hand!

They started out as the starter files that tools/blender/generate_soldier.py writes (see below), but now they're the source, so edit them however you like. The script won't overwrite them unless you tell it to (--force).

Setting up

  1. Install the add-on: Edit > Preferences > Add-ons > Install from Disk, and pick tools/blender/lastfleet_rigs.py. Enable Last Fleet Rigs. Its tools are in the 3D view's sidebar (N), on the Last Fleet tab, in the Rig panel.

  2. Set Rig file to the rig the body is built on: content/rigs/humanoid.json in the repository. The add-on reads it for everything below, and writes its output next to it (content/characters, content/anim).

  3. Starting fresh? Build rig makes the rig's armature with its bones named and placed as the file says, and sets the scene to 30 frames a second, which is the rate the game plays animations at. Working on the soldier? Set the scene to 30 fps (Output Properties > Frame Rate) before File > Import > glTF, or the keys land between frames.

  4. Guides adds back the things that help you fit the model, for example after an import:

    • the sockets: small spheres on their bones that mark where the camera sits and where the hands hold the gun;
    • the body the simulation shoots at: wire capsules for the collision shape and the narrower shape shots hit, small spheres for the eye standing and crouched, and the head sphere that shots hit over each eye.

    Guides are never exported.

What the game reads

What How
The rig One armature with exactly the rig's bones, under the parents the rig gives. A model's bones can be longer or shorter than the rig's (longer arms, longer legs with a shorter spine). The game keeps each model's own build when the rig's clips play on it (see below). Each bone has to point the same way as the rig's, within 5°, without being turned or rolled (the clips rotate it from there). The root stays on the origin, and the eye stays where the rig has it at rest, within 5 cm up or down and 10 cm sideways (because that's where shots hit the head).
The body Meshes skinned to the armature: an Armature modifier and vertex groups named after its bones, at most four bones per vertex. The style is low-poly parts, each weighted fully to one bone.
Its size Meters. The body faces +Y, +Z is up, and its feet are on the origin. Fit it to the guides: the simulation's capsule (0.35 m radius, 1.8 m tall) and the head sphere around the eye (1.65 m up when standing). Shots hit those shapes, not the mesh. A designer fits them to the bodies in Studio (Bodies, Rig tab: the rig's body).
Shading Flat: each face is lit by its own normal.
Colors A material's Base Color. Materials named Paint_<Slot> (Paint_Uniform, Paint_Armor) can be recolored per variant, the same as weapon and prop paint slots.
Surface materials How each material reacts to light (cloth, painted metal, glass, a visor, a glowing signal). You pick it with the Last Fleet Materials add-on, and it's exported as the material's custom property (materials.md).
The clips Actions on the armature, named the same as the rig's clips (the panel lists them).

The humanoid's bones

Root (on the ground; it never moves), Hips, Spine, Chest, Neck, Head; Shoulder, UpperArm, LowerArm and Hand on each side; UpperLeg, LowerLeg and Foot on each side. Left is .L (Blender's -X) and right is .R. The rest pose is a T pose.

The humanoid's clips

Clip Played Notes
Idle A loop Standing, with the gun held ready.
Walk_F, Walk_B, Walk_L, Walk_R Loops One stride forward, backward, and to each side while facing ahead. The game blends them by the direction of movement, and plays them as fast as the body covers ground, so the feet keep pace.
Run_F, Run_B, Run_L, Run_R Loops The same, running.
Crouch, CrouchWalk_F (_B, _L, _R) Loops Crouched, standing still and moving. The crouched eye is 1.1 m up.
Fire Once, upper body The kick from one shot.
Reload Once, upper body Played on top of whatever the legs are doing, so it can run and reload at the same time.
Throw Once, upper body A grenade.
LeanLeft, LeanRight Held at the last frame Leaning all the way out around cover. The game blends toward it based on how far the body leans.
BlindFire Held at the last frame The gun held up over cover, with the head kept down.
Downed A loop On the deck, hurt, with the sidearm still up.
Death Once Falling dead. It stays in its last pose.
Pistol_Idle, Pistol_Fire, Pistol_Reload Same as their rifle clips For a pistol (the pistol grip): held out in both hands, the kick flipping up, the magazine being changed. The arms in Pistol_Idle are also how a pistol is held while walking and running.

Clips for a grip. A gun's frame says how it's held (its grip, see animation-graphs.md). A grip plays the rig's clips named after it, <Grip>_<Clip>, instead of the rig's normal ones, and falls back to the normal ones where it has none. So you only make the clips that need to be different (the hold, the kick, the reload), list them in the rig file, and export the clips.

Keep the eye where the simulation has it. This one bites people, so here's why it matters. A clip the rig marks as "eye": "standing" (Idle, the walks and runs, Fire, Reload, Throw) or "crouched" (the crouches) has to keep the Eye socket within 5 cm up or down and 10 cm sideways of the eye guide (1.65 m standing, 1.1 m crouched, as far forward as the socket is at rest). That's where the simulation puts the head sphere, so a head drawn higher or further forward gets shot straight through.

A bob and a sway are fine. A stride that leans the head well forward, or a crouch that keeps it high, isn't. The fix? Move the hips (down for a deeper crouch, back under a lean) to bring the eye to the guide. Check measures it, and Studio's Bodies mode shows it (Hit shapes).

In place. The simulation moves the body; a clip never does. Root is never keyed away from the origin (Check rejects that), and the hips stay over the feet, so a stride is walked on the spot. Loops end where they start: key the last frame the same as the first. Use the panel's clip buttons to step through each one.

Models of other builds (retargeting)

The clips are animated on the rig's armature, with its bones where the rig puts them. But what if a model is built differently: longer arms, longer legs and a shorter spine, or a stockier frame? The game keeps each model's build while the clips play, the same way Unreal's translation retargeting does. Each bone in the rig has a translation setting (content/rigs/<id>.json):

  • skeleton (the default): the bone keeps the model's own offset from its parent, and the clip only rotates it. A longer forearm stays longer in every clip.
  • scaled: uses the clip's offset, scaled by how much longer the model's bone is than the rig's. The humanoid's hips use this, so a model with higher hips bobs and drops them by the same amount relative to its size.
  • animation: uses the clip's offset unchanged (the humanoid's root, which never moves).

The sockets move with the model's own bones, so a longer arm carries its grip further out.

There are two things a model can't change:

  • Which way its bones point. The clips rotate each bone from its rest pose, so a bone pointing another way bends another way.
  • Where its eye is. Shots hit the head where the rig has it.

So keep the head where the guides put it, and change the body below it and the limbs around it. Studio's Bodies mode can show two models side by side on the same parameters (Compare), and its Rig tab sets each bone's translation.

Checking and exporting

Check reports anything the game wouldn't read:

  • no armature, or more than one;
  • a bone that's missing, extra, or under the wrong parent;
  • a model's bone pointing away from the rig's (by more than 5°), its root off the origin, or its eye away from the rig's;
  • a bone in a clips armature moved from where the rig puts it;
  • a mesh with no Armature modifier, unweighted vertices, or vertices with more than four bones;
  • a missing clip, a scene that isn't at 30 fps, or a clip starting or ending between frames;
  • a clip keying a bone the rig doesn't have, or moving the root;
  • a loop that ends away from where it started, or a clip that keeps the eye away from the simulation's.

There are two export buttons:

  • Export model writes the meshes and the armature, with no animation, to content/characters/<Model>.gltf.
  • Export clips writes the armature and every action, with no meshes, to content/anim/<rig>.gltf (humanoid.gltf). These are the clips every model on the rig plays.

Both run the check first, and write one .gltf with its buffers inside it (no .bin). Save the .blend in content/raw/characters/ and commit it together with the .gltf (the .blend goes through Git LFS).

Got a pile of files to export? You can do every source file at once, the same way the buttons do (each one checked first, and nothing written if there's a problem): python3 tools/blender/export_characters.py content (or blender --background --python tools/blender/export_characters.py -- content). Name files to export only those (... content soldier humanoid_clips). dotnet test tests/LastFleet.Content.Tests checks the shipped soldier and clips against the rig.

Adding clips to the rig

List the new clip in the rig file (content/rigs/<id>.json, clips), then make it in <rig>_clips.blend and export (Check names any clip the rig lists that the file is missing).

Some clips can be posed by the generator (its CLIPS list in tools/blender/generate_soldier.py, which includes the pistol's). For those, python3 tools/blender/generate_soldier.py content --add-clips adds every listed clip that humanoid_clips.blend is missing, posed the same way as the starter clips, leaves the existing actions alone, and exports the file. Too easy!

Making the starter files again

python3 tools/blender/generate_soldier.py content (with Blender's Python module, pip install bpy), or blender --background --python tools/blender/generate_soldier.py -- content, builds the rig from its file, the grey-box soldier, the lancer, the player, and every clip.

The clips are posed with simple IK: feet planted, hands on a rifle's grips, and the hips moved so the eye is where the simulation has it, on average, through each clip the rig marks with an eye. It saves them as the source files above and exports them. Name a model (... content lancer) to make only that model's file.

A couple of gotchas:

  • It stops if the files already exist, which they will once anyone has worked on them.
  • --force writes the starter files back over them. Be sure you mean it!

A new model for an enemy

One model on a rig can be the look for any number of enemies. Here's the flow:

  1. Model it on the rig as above (start from a copy of soldier.blend, saved as content/raw/characters/<model>.blend).
  2. Export it to content/characters/<model>.gltf.
  3. Set it as the variant's model in content/defs/ai/enemies.json (in Studio: Behavior > Enemies), along with its body (the body type, humanoid).

Studio's Bodies mode shows it playing its clips (--mode bodies --body humanoid:<model>). The clips belong to the rig and are shared, so the new model doesn't need any of its own.

A new kind of body

A rig is just a file! Copy content/rigs/humanoid.json to <id>.json and change it, either in a text editor or in Studio's Bodies mode, Rig tab (which draws the skeleton as you edit). It holds:

  • its bones (a parent comes before its children; head and tail in the rest pose, in the game's axes: +Y up, -Z forward, +X to the body's right);
  • its sockets;
  • its IK chains (a run of bones from root to tip, the direction its middle joint bends, and what it reaches for: grip, ground or look);
  • its masks (from these bones down, except the ones listed);
  • the mask hidden in first person;
  • the body the simulation shoots at;
  • its clips.

Build rig then makes its armature. The game checks every rig when it reads it and reports every problem.
