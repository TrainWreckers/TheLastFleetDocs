What one client knows about the horde, kept on the host, and the horde's part of that client's snapshots. It stays within the design's budget (64 kbps for everything) no matter how many swarmlings there are.

Remarks

There are two parts. First a table of the swarmlings near the client (within Range), each in a slot it keeps while it stays near: their ids, then one bit each for the dead. The table only changes as swarmlings arrive, leave and die, so the delta against the client's last acknowledged snapshot costs almost nothing. Then come updates, packed to about 8 bytes each: where some of the swarmlings are (to 3 cm, relative to the client's feet), which way they're moving and facing, and what they're doing. Each snapshot gets as many updates as the client's budget has room for after the rest of the fight is sent (Fit(int)), between 2 and 16. With 300 nearby, each one gets updated about every one to four seconds.

The client draws each swarmling along its updates (LastFleet.Networking.Replication.SwarmTrack), and the host keeps the same tracks, so it knows where the client is drawing every swarmling. The host updates the ones drawn farthest from their real position first, weighted by how close they are to the client (one at the client's feet is kept to within centimeters, one 60 m away to half a meter), and also updates each one now and then regardless. A swarmling that starts a lunge within reach of a player is updated immediately (the wind-up is the player's warning), and a new one is placed immediately. The same tracks are used to resolve the client's shots at the horde (TryShown(int, double, out Vector3, out float, out SwarmSurface), for lag compensation), so the client hits what it was shown.

Doesn't allocate after the first few snapshots.
